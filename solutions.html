Authentication

FIDO2 authentication with custom-defined scenario functions.

FIDO2/WebAuthn provides a standard path for phishing-resistant user authentication. IIST uses this path as the user-facing authentication layer, then supports companion scenario functions anchored in hardware-rooted trust.

Important note: IIST custom-defined functions are not part of the FIDO2 standard. They are companion functions designed around IIST hardware-rooted trust capabilities and the customer's deployment scenario.
  • Administrator access for routers, gateways, and management systems
  • Operator authentication for industrial systems
  • Role-separated access for service, firmware, data, or maintenance functions
  • Hardware-bound challenge-response for device identity
  • Secure provisioning and lifecycle events
  • Local protection or signing workflows tied to a trusted hardware anchor

Standard FIDO2 / WebAuthn path

User->Browser / App->FIDO2 Authenticator->Server

IIST companion trust path

IIST Hardware Trust->Challenge-Response->Device Identity->Lifecycle Function

Example scenario: secure router administrator access.

  1. An administrator signs in using a FIDO2-capable hardware trust key.
  2. The service verifies the WebAuthn authentication.
  3. The device or management platform requests a hardware-rooted companion challenge-response.
  4. IIST hardware proves that the operation is tied to the expected trust anchor.
  5. Firmware update, configuration change, or log signing proceeds under a separated trust path.

Provenance

C2PA-compatible provenance for content and machine data.

As AI-generated content and machine-generated data increase, provenance becomes more important than detection alone. IIST supports C2PA-compatible workflows where content, logs, sensor outputs, inspection records, or robotic evidence can be signed and verified with hardware-rooted trust.

  • Signed images and documents
  • Machine logs
  • Sensor data
  • Robotic inspection outputs
  • Industrial records
  • AI data pipeline evidence
  • Internal enterprise signing and verification
Capture / Create->Hash->Sign Provenance->Attach Manifest->Store / Publish->Verify
C2PA notice: IIST supports C2PA-compatible content authenticity workflows. Official C2PA Trust List / root certificate registration is pending, so public validators may not yet recognize IIST-issued signatures as trusted under the official C2PA trust model. Qualified customers can discuss private, enterprise, pilot, or staged trust-chain deployment models.

Robotics and AIoT

Trust for robotics before action.

Robots are becoming physical actors in the real world. Before a robot moves, updates, reports, or accepts remote commands, it should be able to prove who it is, what state it is in, where its data came from, and which operator, model, or policy authorized the action.

IIST's vision is to make trust portable across robot identity, operator authentication, sensor provenance, firmware lifecycle, and fleet operation. The goal is not only secure login. The goal is evidence of trusted operation.

  • Robot and controller identity
  • Operator authentication
  • Sensor and log provenance
  • Signed inspection reports
  • Secure firmware update path
  • Tool, model, or policy authorization
  • Fleet onboarding
  • Device-to-cloud trust
  • Long-life field-device lifecycle
Robot Identity->Operator Authorization->Firmware Trust->Sensor Evidence->Verified Report

Hardware Traceability

PUF-based trust tracking for chips, modules, and chiplets.

Careful language: A PUF-derived hardware identity can act as a hardware-rooted fingerprint. It can support enrollment, verification, traceability, and lifecycle evidence. It does not by itself guarantee the security of an entire supply chain; it becomes valuable when combined with the right manufacturing flow, database, policy, and verification process.
